# 当前技术决定

## 本机阅读与职责

阅读由本机服务提供，不调用模型。React 管页面与交互，domain 管字数／修订，data 管 PRTS 取数与解析，storage 管记录／缓存，server 管业务服务和协议适配。使用现有 SDK、SQLite 和原生动画 API，不为未实现功能新增框架。

## 来源与解析

目录范围固定为 PRTS 剧情一览正文，保留稳定 ID 与源顺序。扫描源字段后明确选择简单或复杂分支流程，人物与图层状态按分支隔离，共同后续只出现一次。

源格式中的固定名称、兼容白名单、资料索引及图层坐标有明确用途与来源；依据、适用范围和变化后的检查见 [PRTS 维护规则](../docs/maintenance.md)。未知正文或资源不能靠猜测兜底。

## 进度与持久化

打开当前剧情后准备该部全部正文以取得字数分母；准备过程只写公共缓存／统计，实际打开正文才登记阅读与执行修订迁移。最后位置和最远进度分开保存，未知分母不当作零。

阅读记录、内容缓存和字数索引使用独立 SQLite 存储。事务支持多进程；清理代次和 historyToken 阻止迟到请求恢复已清数据；旧 JSON 迁入标记防止重复导入。现有磁盘／工具契约的兼容不因内部拆分改变。

## 图片与封面

姓名与资源分别处理，匿名不揭示真实身份。多人匹配需要精确资料与唯一场景资源；原图不可用时只选择有来源的同造型默认，不能确认则占位。网络与解析失败保持可重试错误。

封面按源资料定位，统一 1560:500 外框，批准的非横幅完整显示；两个同名特殊合集因无唯一图片，按稳定 ID 使用不同文字封面。具体 ID、尺寸和资料来源见[封面规则](../docs/requirements.md#封面)。

图片保持原始字节和透明通道，MCP 通过 app-only 元数据分段传输。图片预算及其维护依据见[图片与传输预算](../docs/maintenance.md#图片与传输预算)。

## 页面与设计

位置观察、保存队列和动画各自处理生命周期；状态提交、页面切换和恢复位置保持一致，取消或迟到导航不得覆盖当前页面。保存失败不跳过后续已排队写入。

设计预览复用正式 UI 入口，不维护另一套组件、静态原型状态或独立素材。行为说明只描述当前实现；旧方案只在兼容规则或明确禁用理由需要时提及。

## 运行包与发布

GitHub 保存源码与 CI，npm 保存完整运行包，稳定 marketplace 固定精确 npm 版本。系统 Node 是运行前提；标准 npm pack 内嵌生产依赖，正式入口仅 PRTS，源码和独立开发副本保留 fixture。

普通 push／PR 在 Ubuntu 执行通用检查；标签发布前保留 Windows 运行包与真实 PRTS 验收，覆盖当前目标平台，不设置三平台矩阵。npm 发布 job 在 Ubuntu 使用 OIDC 上传同一归档为 next，仅该 job 绑定 `npm-production` 环境审批。

稳定提升保留手动触发、真实宿主验收确认及标签／回执／registry integrity 校验，不绑定 environment。个人维护项目由同一人发起和批准，手动触发及验收确认已承担稳定提升的发布决定，不增加第二次 environment 审批。稳定 marketplace 始终固定精确 npm 版本。

阅读记录、原文／图片缓存、临时工具和恢复备份不进入发行物。

## Windows 验收解压目录（2026-11-06）

首次 Windows 标签验收在系统 tar 的 `-C` 参数上丢失中文目录；本机用含中文／特殊字符的真实目录复现了旧调用失败、进程 `cwd` 调用成功。验收工具改用 Node 原生工作目录传递目标，并先解析归档绝对路径以保留相对输入语义。不改系统区域设置，不删除中文覆盖，也不新增解压依赖；原 package/ 条目限制与超时保持不变，新增真实归档回归防止退回旧调用。

改动仅限验收工具、回归与交接记录，不改变包内阅读器或持久化格式。该修复已按用户授权提交／推送为 `21d196d`，Ubuntu Check 通过；用户另行明确授权后，未发布标签 `v1.0.0` 已重建到该提交。后续再次移动标签仍须另行确认，没有重发或覆盖 npm 包。

## Windows 验收关闭与本地预检（2026-11-06）

第二次 Windows CI 的 finally 只留下删除临时目录的 EBUSY，不能据此确定被覆盖的原始失败。已在本机通过真实子进程复现独立的清理竞争：当前 MCP client SDK 的失败握手会启动异步 close，第二次 close 可在首次关闭完成前返回；若子进程仍持有 cwd，立即删除目录会失败。

验收工具先登记连接所有权，保留 transport，并等待公开 onclose 事件。关闭事件等待上限 5 秒，依据当前锁定 SDK 两次各 2 秒的退出宽限加事件交付余量；升级 SDK 后核对其关闭实现及延迟退出回归。目录清理使用 [Node fs.rm](https://nodejs.org/api/fs.html#fspromisesrmpath-options) 的 5 次、100ms 线性退避，容纳短暂 Windows 句柄锁，持续锁定仍失败。验收失败与清理失败以原始错误优先共同报告，不能用重试隐藏原始失败；未放宽 MCP 初始化或解压超时。

包验收记录阶段与耗时，清理结束后才写成功报告。真实子进程覆盖握手超时／延迟退出，以及短暂和持续 cwd 锁；故障注入覆盖原始失败与多项清理失败同时发生。复用已有脚本支持 Windows 本地候选预检，不新增发布环境、检查矩阵或依赖。本地通过不替代最终标签 CI、OIDC 和真实桌面验收。本轮已获统一提交／推送授权，继续使用本机默认个人 Git 署名；再次更新未发布标签及发布仍分别等待用户明确确认。

## npm 准备与 MCP 握手时限（2026-11-06）

`7833ace` 的 Windows CI 已证实上述关闭／清理修复通过；保留下来的原始错误是 npx 初始化 60 秒超时，直接 manifest／bin 与工具／HTML 均成功。旧脚本由 SDK 拉起 npm 后立刻开始握手，npm 的冷缓存安装和 CLI 准备也消耗同一握手时限；仅凭该日志不能确定 npm 内部具体耗时分布。

按 [npm exec 官方行为](https://docs.npmjs.com/cli/v12/commands/npm-exec/)，先对同一 tgz 使用全新隔离缓存、`--offline --ignore-scripts` 和当前 Node 的 `--version`，等待 npm 准备结束；再从同一缓存启动真实 bin，继续原有 MCP／HTML／持久化验收。安装过程使用既有 npmCommand 的 120 秒限时，SDK 握手仍为默认 60 秒，不放宽协议请求或忽略失败。真实 fixture tgz 检查安装脚本未运行，并用缓存安装目录中的标记验证后续执行确实复用该安装。

这只调整验收脚本的阶段边界，不更改发布流程、生产依赖、运行入口或版本。本地定向与实际 tgz 离线／PRTS 验收通过，新的 Windows CI 结果仍待提交及标签更新后核验。
