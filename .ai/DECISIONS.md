# 当前技术决定

## 本机阅读与职责

阅读由本机服务提供，不调用模型。React 管页面与交互，domain 管字数／修订，data 管 PRTS 取数与解析，storage 管记录／缓存，server 管业务服务和协议适配。使用现有 SDK、SQLite 和原生动画 API，不为未实现功能新增框架。

## 来源与解析

目录范围固定为 PRTS 剧情一览正文，保留稳定 ID 与源顺序。扫描源字段后明确选择简单或复杂分支流程，人物与图层状态按分支隔离，共同后续只出现一次。

源格式中的固定名称、兼容白名单、资料索引及图层坐标有明确用途与来源；依据、适用范围和变化后的检查见 [PRTS 维护规则](../docs/maintenance.md)。未知正文或资源不能靠猜测兜底。

## 进度与持久化

打开当前剧情后准备该部全部正文以取得字数分母；准备过程只写公共缓存／统计，实际打开正文才登记阅读与执行修订迁移。最后位置和最远进度分开保存，未知分母不当作零。

阅读记录、内容缓存和字数索引使用独立 SQLite 存储。事务支持多进程；清理代次和 historyToken 阻止迟到请求恢复已清数据；旧 JSON 迁入标记防止重复导入。现有磁盘／工具契约的兼容不因内部拆分改变。

## 图片与封面

姓名与资源分别处理，匿名不揭示真实身份。多人匹配需要精确资料与唯一场景资源；原图不可用时只选择有来源的同造型默认，不能确认则占位。网络与解析失败保持可重试错误。

封面按源资料定位，统一 1560:500 外框，批准的非横幅完整显示；两个同名特殊合集因无唯一图片，按稳定 ID 使用不同文字封面。具体 ID、尺寸和资料来源见[封面规则](../docs/requirements.md#封面)。

图片保持原始字节和透明通道，MCP 通过 app-only 元数据分段传输。图片预算及其维护依据见[图片与传输预算](../docs/maintenance.md#图片与传输预算)。

## 页面与设计

位置观察、保存队列和动画各自处理生命周期；状态提交、页面切换和恢复位置保持一致，取消或迟到导航不得覆盖当前页面。保存失败不跳过后续已排队写入。

设计预览复用正式 UI 入口，不维护另一套组件、静态原型状态或独立素材。行为说明只描述当前实现；旧方案只在兼容规则或明确禁用理由需要时提及。

## 运行包与发布

GitHub 保存源码与 CI，npm 保存完整运行包，稳定 marketplace 固定精确 npm 版本。系统 Node 是运行前提；标准 npm pack 内嵌生产依赖，正式入口仅 PRTS，源码和独立开发副本保留 fixture。

普通 push／PR 在 Ubuntu 执行通用检查；标签发布前保留 Windows 运行包与真实 PRTS 验收，覆盖当前目标平台，不设置三平台矩阵。npm 发布 job 在 Ubuntu 使用 OIDC 上传同一归档为 next，仅该 job 绑定 `npm-production` 环境审批。

稳定提升保留手动触发、真实宿主验收确认及标签／回执／registry integrity 校验，不绑定 environment。个人维护项目由同一人发起和批准，手动触发及验收确认已承担稳定提升的发布决定，不增加第二次 environment 审批。稳定 marketplace 始终固定精确 npm 版本。

阅读记录、原文／图片缓存、临时工具和恢复备份不进入发行物。

## Windows 验收关闭与本地预检（2026-11-06）

第二次 Windows CI 的 finally 只留下删除临时目录的 EBUSY，不能据此确定被覆盖的原始失败。已在本机通过真实子进程复现独立的清理竞争：当前 MCP client SDK 的失败握手会启动异步 close，第二次 close 可在首次关闭完成前返回；若子进程仍持有 cwd，立即删除目录会失败。

验收工具先登记连接所有权，保留 transport，并等待公开 onclose 事件。关闭事件等待上限 5 秒，依据当前锁定 SDK 两次各 2 秒的退出宽限加事件交付余量；升级 SDK 后核对其关闭实现及延迟退出回归。目录清理使用 [Node fs.rm](https://nodejs.org/api/fs.html#fspromisesrmpath-options) 的 5 次、100ms 线性退避，容纳短暂 Windows 句柄锁，持续锁定仍失败。验收失败与清理失败以原始错误优先共同报告，不能用重试隐藏原始失败；未放宽 MCP 初始化或解压超时。

包验收记录阶段与耗时，清理结束后才写成功报告。真实子进程覆盖握手超时／延迟退出，以及短暂和持续 cwd 锁；故障注入覆盖原始失败与多项清理失败同时发生。复用已有脚本支持 Windows 本地候选预检，不新增发布环境、检查矩阵或依赖。本地通过不替代最终标签 CI、OIDC 和真实桌面验收。本轮已获统一提交／推送授权，继续使用本机默认个人 Git 署名；再次更新未发布标签及发布仍分别等待用户明确确认。

## npm 准备与 MCP 握手时限（2026-11-06）

`7833ace` 的 Windows CI 已证实上述关闭／清理修复通过；保留下来的原始错误是 npx 初始化 60 秒超时，直接 manifest／bin 与工具／HTML 均成功。旧脚本由 SDK 拉起 npm 后立刻开始握手，npm 的冷缓存安装和 CLI 准备也消耗同一握手时限；仅凭该日志不能确定 npm 内部具体耗时分布。

按 [npm exec 官方行为](https://docs.npmjs.com/cli/v12/commands/npm-exec/)，先对同一 tgz 使用全新隔离缓存、`--offline --ignore-scripts`，等待 npm 准备结束，再启动实际安装的包。安装过程使用既有 npmCommand 的 120 秒限时，SDK 握手仍为默认 60 秒。`fe8919c` 曾让第二阶段的 MCP 管道继续穿过 npm；第四次 Windows 运行在准备 91.5 秒成功后仍初始化超时，因此仅分开时限不足，当前处理见下文。

这只调整验收脚本的阶段边界，不更改发布流程、生产依赖、运行入口或版本。本地定向与实际 tgz 离线／PRTS 验收通过，新的 Windows CI 结果仍待提交及标签更新后核验。

## Windows npm 包装层与实际部署入口（2026-11-06）

官方仓库的 [npm/cli #9959](https://github.com/npm/cli/issues/9959) 报告 Windows 的 npx 管道 stdin 可能挂起，当前仍开放；报告使用 npm 10，不能据此断言本项目 npm 12 具有同一缺陷。本项目第四次 CI 的直接 Node 握手成功、npm 包装层超时且在关闭 stdin 后才启动 bin，支持将问题定位在 npm 启动／输入层，而非机器不能处理 MCP。

正式 mcp.json 已固定系统 Node 入口，因此验收按实际部署路径拆分：npm 非交互安装实际 tgz，明确关闭安装命令 stdin；通过 npm exec 提供的 PATH 用 Node 解析 package.json，验证 Node、包身份、bin 和 realpath 位于全新隔离缓存内。MCP 由系统 Node 直接启动该安装产物的 bin，不经过 npm stdio 转发。保留全部工具／HTML／图片／记录断言，模拟卸载同时删除解包与 npm 安装副本。不为 npm 安装层额外增加 MCP 包装入口支持承诺，也不把它归为已通过的测试。

该发现路径来自 npm exec 的公开 PATH 契约，不固定 _npx 哈希或开发者安装路径；包名作为 argv 传入，不拼接脚本。npmCommand 的现有调用均为非交互 pack／ls／版本／OIDC publish，关闭 stdin 不影响用户在网页完成登录或审批。fixture 回归验证安装来源、安装目录复用与 stdin EOF，实际包协议及 PRTS 验收验证真正运行的缓存内产物。

## Windows 冷安装预算与完整验收复用（2026-11-06）

第五次 Windows Release 的第一遍 npm 冷安装准备 107,174ms 成功，真实安装产物 Node 握手 340ms 通过；第二遍独立 PRTS 验收在冷安装准备 120,028ms 后被通用命令时限终止。直接失败来自脚本的 120 秒上限，不能归为 Actions 审批／OIDC、MCP 不兼容或已确认的业务错误；npm 内部耗时阶段尚缺证据。

`--prts` 改为先完成默认模式同样的三个入口工具／HTML 离线检查，再运行全部真实来源与记录断言；一次隔离验收只冷安装一次，后续重开使用同一已验证目录。Windows 只运行这一完整调用，普通 Ubuntu Check 保留默认离线调用。每次仍从空缓存消费实际 tgz，不用跨运行热缓存、跳过安装或删除断言换取通过。

以已经观察到的 107 秒成功与 120 秒终止为依据，仅安装阶段使用有界 300 秒预算；其他 npm 命令仍为 120 秒，SDK 握手仍为 60 秒。按 [npm 官方日志文档](https://docs.npmjs.com/cli/v12/using-npm/logging/) 启用 timing／verbose、实时输出，并将日志放到临时目录外；工作流失败后仍保存诊断 artifact，后续以实际阶段计时定位耗时。本地计时另外观察到 npm 自身更新请求，因此仅对该离线准备命令关闭 update-notifier；固定工具链不需要自动发现新版本，CI 原本也跳过此通知。

用户明确确认保留完整验收并持续推进至服务器 Release 验收通过，原有必要修复、提交／推送和未发布候选标签更新授权继续有效。npm-production 网页发布审批仍由用户完成，稳定提升与真实桌面验收不在本次服务器自动验收结果内。

## 触摸回归以实际滚动和下一次操作验收（2026-11-06）

第六次 Windows CI 已通过完整实际包／PRTS 验收，浏览器唯一失败为横滑后的 scrollend 测试标记未触发；scrollLeft 大于 50 的断言已通过，其余 33 项通过。页面产品代码不依赖 scrollend，本地 Edge 156 的原测试连续三次通过，因此不为该测试事件改动产品滚动实现，也不宣称已确认 Chromium 的具体缺陷。

第七次 Windows 结果证明该观察条件仍不足：后续 tap 没有生成 click，未打开正文。此 200ms 替代方案已由下述同版浏览器对照修复取代。

## 原生触摸输入按实际帧节奏注入（2026-11-07）

本地用与 CI 相同的 Windows Chromium headless shell 156.0.8078.4 复现了第七次失败。原快速注入有 pointercancel／touchend，后续 tap 有 pointerdown／pointerup／touchstart／touchend 却无 click；延迟 CDP detach 仍失败，触摸能力前后均为 1。仅把原有 touchMove 按 requestAnimationFrame 的真实帧节奏发送，同一次 tap 随即生成 click。恢复原 scrollend 断言后，连续三次及完整 34 项通过，支持将当前问题定位到测试注入时序，而非修改产品点击行为。

采用最小修复：保留原始可信触摸事件、原生滚动及惯性、scrollend、横滑距离和之后一次点击的所有功能断言，只为每次移动等待实际下一帧；不用固定长等待、点击重试、强制偏移或关闭惯性来取得通过。类型与格式通过，后续仍由服务器完整验收确认。
